## 1. La redondance

**Principe :** en cas de panne d'un équipement, le réseau continue d'assurer son rôle — de façon transparente pour l'utilisateur.

- Tout réseau atteignant une taille importante **devrait** être redondant.
- La redondance coûte cher... mais une panne coûtera bien plus cher !

### Les problèmes qu'elle apporte

Une topologie redondante (plusieurs chemins physiques entre switchs) peut créer une **tempête de diffusion** (broadcast storm) : une trame broadcast tourne en boucle indéfiniment entre les switchs, se multipliant à chaque passage, jusqu'à saturer le réseau. Elle peut aussi provoquer des copies indésirables de paquets et des instabilités de la table ARP.

---

## 2. Le STP (Spanning Tree Protocol)

Permet de garder les bénéfices de la redondance **tout en empêchant ses inconvénients** (boucles, tempêtes de diffusion).

Les switchs communiquent entre eux via des **BPDU** (Bridge Protocol Data Unit), qui contiennent :
- une adresse MAC
- un champ d'identification
- l'état du switch

**Fonctionnement de base :** STP coupe (bloque) le lien redondant tant que tout fonctionne normalement. Si le lien actif est perdu, STP réactive automatiquement le lien redondant qui avait été coupé.

### Le mécanisme en détail

**Étape 1 — Élection du Root Bridge**
- Il ne peut y avoir qu'**un seul Root Bridge** par réseau (par VLAN, en PVST+).
- Il est choisi par son **BID** (Bridge ID), une valeur entre 0 et 65535.
- Le **BID le plus faible l'emporte**.
- Le BID par défaut (priorité) est **32768**.
- **En cas d'égalité de BID :** le switch avec l'**adresse MAC aux bits les plus petits** est désigné Root Bridge.

**Étape 2 — Élection du Root Port**
- Chaque switch non-root doit avoir un **Root Port** : le port par lequel il communique avec le Root Bridge.
- Tous les autres ports d'un switch non-root sont appelés **ports désignés** ou **non-désignés**, selon le BPDU reçu sur chacun.

### Chercher le Root Bridge — en pratique

```
show spanning-tree vlan 1
```
- Si la sortie n'indique pas "this bridge is the root" → ce switch n'est pas root, mais il communique avec le root bridge via son Root Port (ex. FastEthernet0/3).
- Si "This bridge is the root" apparaît → c'est bien le Root Bridge.

**Forcer un switch à devenir Root Bridge pour un VLAN donné :**
```
spanning-tree vlan 1 root primary
```

## 3. Évolutions du STP

- **IEEE 802.1D** : STP original — jugé trop lent pour remonter un lien dans de nombreux contextes.
- **IEEE 802.1w (RSTP — Rapid STP)** : version améliorée, réactivité accrue de l'algorithme.
- **PVST+ (Per-VLAN Spanning Tree +)** : implémentation propriétaire Cisco, avec une **instance STP par VLAN**. C'est le mode **activé par défaut** sur les switchs Cisco.

### Optimiser le STP — jouer sur les délais

```
spanning-tree vlan N° hello SECONDES        ! délai entre les messages STP
spanning-tree vlan N° max-age SECONDES      ! temps de rétention en mémoire des messages Hello
spanning-tree vlan N° forward-delay SECONDES ! temps d'attente avant de changer l'état d'un port
```

### Le mode MST (Multiple Spanning Tree)

Le calcul STP peut consommer beaucoup de ressources sur un switch traversé par de nombreux VLANs (une instance par VLAN en PVST+). Le mode **MST** permet de **soulager l'appareil** en ne faisant tourner **qu'une seule instance STP pour plusieurs VLANs** à la fois.

```
spanning-tree mode mst
spanning-tree mst configuration
region-name NOM_À_DONNER
instance 1 vlan 1,10,20
exit
```
(exemple : une seule instance STP pour les VLANs 1, 10 et 20)

**Résumé des variantes :**
| Norme | Nom | Apport |
|---|---|---|
| IEEE 802.1D | STP original | Base historique, lent |
| IEEE 802.1w | RSTP | Réactivité améliorée |
| — (Cisco) | PVST+ | Une instance STP par VLAN |
| — (Cisco) | MST | Une instance STP pour plusieurs VLANs (économie de ressources) |

## 4. Diagnostiquer des problèmes STP (Troubleshooting)

**Méthodologie en 4 étapes :**
1. Découvrir/connaître la topologie de niveau 2 du réseau
2. Déterminer par raisonnement quel switch **devrait** être le Root Bridge
3. S'assurer que c'est bien le cas
4. Visiter chaque switch pour connaître quels ports sont bloqués ou en mode forward, et confirmer la topologie de niveau 2 attendue

**Commande clé :**
```
show spanning-tree
```
Informations à lire :
- Version de Spanning Tree utilisée (protocole IEEE ou RSTP)
- Root ID (sur la ligne `Root ID`)
- Les délais `Hello Time`, `Max Age` et `Forward Delay`
- Le Bridge ID local
- Le statut des interfaces
- Le coût des interfaces (`Cost`) et leur priorité (`Prio.Nbr`)

## 5. PortFast

Fonctionnalité **propriétaire Cisco**. Permet de faire passer un port de l'état bloqué à **forwarding instantanément**, en sautant les étapes normales de convergence — très utile sur le port d'un switch connecté directement à un **périphérique terminal** (PC, laptop, imprimante...), jamais vers un autre switch.

## 6. BPDU Guard

Principe : si le port n°8 d'un switch est relié à un PC ou un serveur, il ne devrait **jamais** recevoir de BPDU (les BPDU ne s'échangent qu'entre switchs). Si un BPDU est reçu sur ce port, c'est que quelqu'un a remplacé le PC/serveur par un switch — c'est potentiellement une **intrusion**. BPDU Guard détecte les BPDU reçus sur ce type de port et **éteint automatiquement le port**.

→ BPDU Guard est donc une protection qui coupe les ports non-trunk recevant une trame BPDU.

### Mise en place

```
interface TYPE N°
spanning-tree portfast
spanning-tree bpduguard enable
```
(active PortFast et BPDU Guard sur une interface précise)

**Pour activer BPDU Guard globalement sur tous les ports déjà en PortFast :**
```
spanning-tree portfast default
spanning-tree portfast bpduguard default
```

### Vérifier

```
show running-config interface FastEthernet0/1
```

| `spanning-tree vlan N forward-delay SECONDES` | Temps d'attente avant changement d'état d'un port |
| `spanning-tree mode mst` | Active le mode MST |
| `spanning-tree mst configuration` | Entre en config MST (region-name, instance) |
| `spanning-tree portfast` | Active PortFast sur un port |
| `[no] spanning-tree bpduguard enable` | (Dés)active BPDU Guard sur un port |

## Points de vigilance (erreurs à ne pas refaire)
- ⚠️ **`switchport nonegotiate` échoue** (`Conflict between 'nonegotiate' and 'dynamic' status`) si `switchport mode trunk` n'a pas été appliqué avec succès juste avant — toujours vérifier avec `show interface <port> switchport` (ligne `Administrative Mode`) avant d'enchaîner. Piège déjà rencontré sur le TP VLAN/Trunking (Fa0/13) et reproduit ici sur Fa0/4.
- ⚠️ **Commandes non simulées sur Packet Tracer** rencontrées dans ce TP : `debug spanning-tree events` (donc pas de mesure en direct des temps de convergence) et `show running-config interface <port>` (abrégé) → utiliser `show running-config` en entier et repérer le bon bloc `interface`, ou `show spanning-tree interface <port> detail` pour vérifier PortFast spécifiquement.
- ⚠️ **Un port en `err-disabled` (via BPDU Guard, comme via Port Security) ne se réactive jamais tout seul** même après avoir retiré la cause (`no spanning-tree bpduguard enable`) — toujours faire le cycle manuel `shutdown` puis `no shutdown`.

## Tâche 1 — Vérifier les opérations STP

### Étape 1 — Activer un second lien SW1↔SW2 (Fa0/4) en trunk

```
enable
configure terminal
interface fa0/4
switchport mode trunk
switchport trunk allowed vlan 1,10,20
switchport nonegotiate
no shutdown
end
```
(sur SW1 **et** SW2 — recrée volontairement une redondance à 2 liens entre les switchs, pour observer comment STP la gère)

### Étape 2 — Confirmer que STP tourne (`show spanning-tree summary`)

```
SW1#show spanning-tree summary
Switch is in pvst mode
[...]
Name          Blocking Listening Learning Forwarding STP Active
VLAN0001      1        0         0        2          3
VLAN0010      1        0         0        3          4
VLAN0020      1        0         0        2          3

SW2#show spanning-tree summary
Switch is in pvst mode
Root bridge for: default VLAN0010 VLAN0020
Name          Blocking Listening Learning Forwarding STP Active
VLAN0001      0        0         1        1          2
VLAN0010      0        0         1        1          2
VLAN0020      0        0         1        2          3
```
→ **Réponse :** mode **PVST** confirmé sur les deux switchs (correspond bien au PVST+ activé par défaut vu en théorie). SW2 apparaît déjà root bridge pour la plupart des VLANs (dépend des adresses MAC réelles du lab, différent de l'exemple du PDF où c'était SW1).

### Étape 3-4 — Identifier le root bridge et le port bloqué

```
SW1#show spanning-tree vlan 1
Root ID    Priority 32769
           Address  0001.97E2.E471
           Cost     19
           Port     3(FastEthernet0/3)
Bridge ID  Priority 32769
           Address  000C.8517.5092

Interface   Role Sts Cost  Prio.Nbr Type
Fa0/13      Desg FWD 19    128.13   P2p
Fa0/3       Root FWD 19    128.3    P2p
Fa0/4       Altn BLK 19    128.4    P2p

SW2#show spanning-tree vlan 1
Root ID    Priority 32769
           Address  0001.97E2.E471
           This bridge is the root
Bridge ID  Priority 32769
           Address  0001.97E2.E471

Interface   Role Sts Cost  Prio.Nbr Type
Fa0/3       Desg FWD 19    128.3    P2p
Fa0/4       Desg FWD 19    128.4    P2p
```
→ **Réponse :** **SW2 est le root bridge** pour le VLAN 1 (`This bridge is the root`, adresse `0001.97E2.E471`). Sur SW1, **Fa0/3 = Root** (chemin vers le root), **Fa0/4 = Altn/BLK** (bloqué par STP pour casser la boucle entre les 2 liens SW1↔SW2), **Fa0/13 = Desg/FWD** (vers le routeur Branch).

## Tâche 3 — Implémenter STP PortFast

### Étape 1-3 — Mesure du temps de convergence sans PortFast

`debug spanning-tree events` **non simulé sur Packet Tracer** → mesure impossible en direct, mais le principe reste : sans PortFast, un port passe par `blocking → listening → learning → forwarding`, ~30 secondes au total (référence du PDF du TD).

### Étape 4 — Activer PortFast sur Fa0/1 (port de PC1)

```
enable
configure terminal
interface fa0/1
spanning-tree portfast
end
```
(avertissement Cisco normal à l'activation : PortFast ne doit être utilisé que sur un port connecté à un hôte final unique — cohérent avec la théorie : jamais vers un autre switch)

### Vérification

`show running-config interface fa0/1` (abrégé) **rejeté par Packet Tracer** → utilisé à la place :
```
show running-config
```
puis repérage manuel du bloc `interface FastEthernet0/1` → ligne `spanning-tree portfast` confirmée présente.

## Tâche 4 — Implémenter le STP BPDU Guard

### Étape 1-2 — Activer BPDU Guard sur Fa0/3 (test, port vers SW2)

```
enable
configure terminal
interface fa0/3
spanning-tree bpduguard enable
end
```

### Étape 3 — Constat de la coupure automatique

```
SW1#show interfaces fa0/3
FastEthernet0/3 is down, line protocol is down (err-disabled)
```
→ **Réponse :** dès réception d'un BPDU de SW2 (échange normal et permanent entre deux switchs STP), BPDU Guard désactive immédiatement le port — exactement le mécanisme décrit en théorie (un port recevant un BPDU alors qu'il ne devrait voir qu'un hôte final = intrusion suspectée), et le même mécanisme `err-disabled` que pour le Port Security vu dans le premier TD.

**Conséquence transitoire notée :** Fa0/3 étant le lien STP actif principal entre SW1 et SW2, sa coupure a temporairement laissé la connectivité inter-switch dépendre de Fa0/4 (en cours de reconvergence).

### Étape 4-5 — Restaurer Fa0/3

```
enable
configure terminal
interface fa0/3
no spanning-tree bpduguard enable
shutdown
no shutdown
end
```
→ Après vérification que `no spanning-tree bpduguard enable` avait bien été pris en compte (`show running-config`) et un cycle `shutdown`/`no shutdown`, le port est repassé **up, line protocol is up (connected)**.

### Étape 7 — Sauvegarde finale

```
copy running-config startup-config
```
sur SW1 **et** SW2.
