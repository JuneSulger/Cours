## 1. Rappels : TCP, UDP et ports

### 1.1 IP, port et protocole de transport

- **L'adresse IP désigne la machine**, le **port désigne l'application** sur cette machine.
- Un routeur ne s'intéresse normalement qu'à l'en-tête IP. Quand on active du filtrage (ACL étendue, pare-feu), il peut aussi lire l'en-tête TCP/UDP (ports, drapeaux), mais **jamais le contenu** (charge utile) du segment.
- « Le réseau est stupide, l'intelligence se trouve aux extrémités » : TCP n'existe qu'entre le client et le serveur, les routeurs intermédiaires le transportent sans l'interpréter.

### 1.2 Plages de ports

| Plage | Nom | Usage |
|---|---|---|
| 0 – 1023 | Ports bien connus | Services standards (HTTP, SSH, DNS...) |
| 1024 – 49151 | Ports enregistrés (« désignés ») | Applications populaires ou propriétaires |
| 49152 – 65535 | Ports dynamiques (« éphémères ») | Attribués temporairement côté client |

### 1.3 Ports à connaître

| Protocole | Transport | Port(s) | Rôle |
|---|---|---|---|
| FTP | TCP | 20 (données), 21 (contrôle) | Transfert de fichiers |
| SSH | TCP | 22 | Administration à distance chiffrée |
| Telnet | TCP | 23 | Administration à distance **en clair** |
| SMTP | TCP | 25 | Transfert de mails entre serveurs |
| DNS | UDP (et TCP) | 53 | Résolution de noms (TCP pour les transferts de zone et grosses réponses) |
| DHCP | UDP | 67 (serveur), 68 (client) | Attribution d'adresses |
| HTTP | TCP | 80 | Web non chiffré |
| POP3 | TCP | 110 | Récupération de mails |
| NTP | UDP | 123 | Synchronisation d'horloge |
| NetBIOS | UDP/TCP | 137-139 | Découverte / partage Windows historique |
| IMAP | TCP | 143 | Récupération de mails (reste sur le serveur) |
| SNMP | UDP | 161 | Supervision / télémétrie |
| LDAP | TCP | 389 | Annuaire |
| HTTPS | TCP | 443 | Web chiffré |
| SMB | TCP | 445 | Partage de fichiers Windows / Samba |
| SMTPS | TCP | 465 | SMTP chiffré TLS |
| CUPS / IPP | TCP | 631 | Impression |
| LDAPS | TCP | 636 | LDAP chiffré TLS |

### 1.4 TCP vs UDP

| | TCP | UDP |
|---|---|---|
| Nom | Transmission Control Protocol | User Datagram Protocol |
| Mode | **Connecté** (établissement de session) | **Non connecté** |
| Fiabilité | Fiable : pas de perte, pas d'erreur, ordre respecté, pas de doublon | Best-effort : pertes et désordre possibles |
| Mécanismes | Numéros de séquence, ACK, timeout + retransmission, checksum, buffer | Checksum simple uniquement |
| Usage | Web, SSH, Telnet, mail, FTP, SMB, LDAP | DNS, DHCP, streaming, VoIP, visio, jeux en ligne |

**Établissement d'une connexion TCP (three-way handshake)**

```
Client                        Serveur
  | ---------- SYN ----------> |   "je veux me connecter"
  | <------- SYN-ACK --------- |   "d'accord, et moi aussi"
  | ---------- ACK ----------> |   "confirmé" → ESTABLISHED
```

Ce mécanisme explique plusieurs observations du TD (partie 3, compteurs d'ACL).

**Retransmission** : un timer démarre à chaque envoi. Sans accusé de réception avant expiration, l'émetteur **renvoie** le segment qu'il gardait en buffer.

### 1.5 États d'une connexion TCP

| État | Signification |
|---|---|
| LISTEN | Le serveur attend des demandes de connexion |
| SYN-SENT | Le client a envoyé un SYN et attend la réponse |
| SYN-RECEIVED | Le serveur a reçu un SYN et renvoyé un SYN-ACK |
| ESTABLISHED | Connexion ouverte, échange de données possible |
| FIN-WAIT-1 / FIN-WAIT-2 | Fermeture initiée localement, en attente de l'autre côté |
| CLOSE-WAIT | L'autre côté a fermé, attente de la fermeture locale |
| CLOSING | Fermeture simultanée des deux côtés |
| TIME-WAIT | Attente de sécurité avant libération définitive |
| CLOSED | Aucune connexion |

### 1.6 Voir les ports et connexions sous Linux

```bash
# Ports ouverts et processus associés (-i réseau, -P ports numériques, -n pas de résolution DNS)
lsof -i -P -n

# Sockets en écoute : -t TCP, -u UDP, -l en écoute, -p processus, -n numérique
netstat -tulpn

# Remplaçant moderne de netstat, mêmes options
ss -tulpn
```

Utile pour repérer : une connexion suspecte, un service à filtrer, une application qui tourne encore, deux applications en conflit sur le même port.

## 2. Théorie des ACL

### 2.1 Concept

Une **ACL** (Access Control List) est une **liste ordonnée de règles** (ACE, *Access Control Entries*) qui autorisent (`permit`) ou refusent (`deny`) des paquets selon des critères (adresses, protocoles, ports).

Trois principes fondamentaux :

1. **Lecture séquentielle** : les règles sont testées dans l'ordre, de haut en bas.
2. **Première correspondance** : dès qu'un paquet correspond à une règle, l'action est appliquée et **les règles suivantes ne sont pas lues**.
3. **Deny implicite** : toute ACL se termine par un `deny any` **invisible**. Un paquet qui ne correspond à aucune règle est refusé.

```
Paquet → Règle 1 ? ──oui──> action (permit/deny) → FIN
            │non
            ▼
         Règle 2 ? ──oui──> action → FIN
            │non
            ▼
         ...
            ▼
      deny any implicite → paquet refusé
```

**Exemple de piège (slide 29)** :
```
access-list 1 permit any
access-list 1 deny host 10.1.1.1
access-list 1 deny any
```
La première règle correspond à **tout** : les deux `deny` ne sont jamais atteints, 10.1.1.1 passe. D'où la règle d'or : **les règles les plus précises en premier, les plus générales à la fin.**

### 2.2 Types d'ACL

| Type | Critères de filtrage | Numéros |
|---|---|---|
| **Standard** | Adresse IP **source uniquement** | 1-99, 1300-1999 |
| **Étendue** | Source, destination, protocole, ports | 100-199, 2000-2699 |
| Dynamique, réflexive, temporelle, CBAC | Hors programme de ce cours | – |

Les ACL standard et étendues peuvent être **numérotées** ou **nommées**.

### 2.3 Mise en place en 3 étapes

1. **Créer** l'ACL
2. **Définir** une ou plusieurs règles
3. **Appliquer** l'ACL (interface ou lignes vty)

Une ACL créée mais non appliquée **n'a aucun effet**.

### 2.4 Le wildcard (masque générique)

Le wildcard est **l'inverse du masque de sous-réseau** : `wildcard = 255.255.255.255 − masque`.

| Masque | Wildcard | Signification |
|---|---|---|
| 255.0.0.0 | 0.255.255.255 | un /8 |
| 255.255.255.0 | 0.0.0.255 | un /24 |
| 255.255.255.248 | 0.0.0.7 | un /29 (8 adresses) |
| 255.255.255.252 | 0.0.0.3 | un /30 (4 adresses) |
| 255.255.255.255 | 0.0.0.0 | un seul hôte |

**Lecture bit à bit** :
- bit à **0** → ce bit **doit correspondre** à l'adresse de référence
- bit à **1** → ce bit **peut varier**

Exemple du TD : `192.168.1.4 0.0.0.3`

```
Dernier octet de la référence : 4 = 0000 0100
Dernier octet du wildcard     : 3 = 0000 0011
                                         ^^ ces 2 bits varient
Adresses correspondantes : 0000 0100 (.4) → 0000 0111 (.7)
```
→ **192.168.1.4 à 192.168.1.7**. La référence doit être alignée sur un multiple de la taille du bloc (ici 4).

**Raccourcis** :

| Raccourci | Équivaut à | Désigne |
|---|---|---|
| `host 192.168.1.3` | `192.168.1.3 0.0.0.0` | un seul hôte |
| `any` | `0.0.0.0 255.255.255.255` | toutes les adresses |

### 2.5 Syntaxe : ACL numérotée vs nommée

**Numérotée (une seule commande crée l'ACL et la règle)**
```
Routeur(config)# access-list 1 permit 172.16.0.0 0.0.255.255
Routeur(config)# access-list 1 permit host 172.16.0.54
Routeur(config)# access-list 1 deny any
```

**Nommée (création puis règles dans un sous-mode)**
```
Routeur(config)# ip access-list standard NOM
Routeur(config-std-nacl)# permit 192.168.0.0 0.0.0.255
Routeur(config-std-nacl)# deny any
```
Pour une ACL nommée, on précise obligatoirement `ip` et le type (`standard` ou `extended`).

Avantages des ACL nommées : nom explicite, **insertion d'une règle à une position précise** grâce aux numéros de séquence, suppression d'une règle isolée.

**Éviter de mélanger** numéros et noms pour la même fonction : on se retrouve avec des ACL en double, ce qui ralentit les audits, favorise les erreurs, complique le dépannage et l'arrivée d'un nouvel admin.

### 2.6 Appliquer une ACL

| Cible | Commande | Mode | Effet |
|---|---|---|---|
| Interface | `ip access-group NOM in\|out` | `(config-if)#` | Filtre le trafic qui **traverse** l'interface |
| Lignes vty | `access-class NOM in` | `(config-line)#` | Filtre qui peut **ouvrir une session d'administration** sur l'équipement |

- `in` : trafic qui **entre** dans l'interface / sur la ligne
- `out` : trafic qui **sort** de l'interface

**Règle des 3P** : au maximum **une ACL par Protocole (IPv4/IPv6), par Port (interface), par sens (in/out)**.

### 2.7 Où placer une ACL ?

- **ACL étendue → au plus près de la source** : elle sait identifier précisément le trafic, donc on le bloque avant qu'il ne consomme de la bande passante.
- **ACL standard → au plus près de la destination** : elle ne connaît que la source ; placée trop tôt, elle bloquerait cette source vers **toutes** les destinations.

### 2.8 ACL étendues (aperçu)

```
access-list 100 deny tcp 192.168.1.0 0.0.0.255 192.168.2.0 0.0.0.255 eq 22
!           |    |    |   |                     |                     └ port destination = 22 (SSH)
!           |    |    |   |                     └ réseau destination
!           |    |    |   └ réseau source
!           |    |    └ protocole
!           |    └ action
!           └ numéro (100-199 = étendue)
```

**Numéros de protocole IP** (utilisables à la place du nom, sans rapport avec les ports) :

| Protocole | N° |
|---|---|
| ICMP | 1 |
| TCP | 6 |
| UDP | 17 |
| IPv6 (encapsulé) | 41 |
| GRE | 47 |
| EIGRP | 88 |
| OSPF | 89 |
| PIM | 103 |

**Opérateurs de port** :

| Opérateur | Signification |
|---|---|
| `eq` | égal à |
| `neq` | différent de |
| `gt` | supérieur à |
| `lt` | inférieur à |
| `range x y` | compris entre x et y |

### 2.9 Modifier ou supprimer

```
! Supprimer une ACL entière (numérotée)
Routeur(config)# no access-list 1

! Supprimer une ACL nommée entière
Routeur(config)# no ip access-list standard NOM

! Supprimer une règle précise d'une ACL nommée
Routeur(config)# ip access-list standard NOM
Routeur(config-std-nacl)# no 20              ← par numéro de séquence
Routeur(config-std-nacl)# no permit host 10.1.1.1   ← ou en recopiant la règle

! Insérer une règle à une position précise
Routeur(config-std-nacl)# 5 permit host 192.168.1.3
```

⚠️ Sur une ACL **numérotée** en syntaxe classique, `no access-list 1 ...` supprime **toute** l'ACL, même si on recopie une seule règle.

**Bonne pratique pour les grosses modifications** : copier les ACL dans un éditeur de texte, les modifier, supprimer l'ACL sur l'équipement, puis recoller la version complète.

## 3. Corrections et précisions sur les supports

| Où | Écrit dans le support | Correction / précision |
|---|---|---|
| Slide 6 (ACL) | « Une ACL par interface » | Une ACL par interface **par sens et par protocole** (règle des 3P) |
| Slide 14 (ACL) | `Routeur(config)#ip access-group` | La commande se tape en mode **interface** : `Routeur(config-if)#` |
| Slide 36 (ACL) | GRE = 41 | GRE = **47** (41 = IPv6 encapsulé) |
| Slide 38 (ACL) | `nq` | L'opérateur est **`neq`** |
| Slide 44 (ACL) | `access-list standard\|extended NOM` | **`ip access-list`** standard\|extended NOM |
| Slide 44 (ACL) | Suppression de règle « possible qu'au sein des ACL nommées » | Vrai en syntaxe classique ; sur IOS récent, une ACL numérotée peut aussi être éditée via `ip access-list standard 1` |
| Slide 37 (TCP/UDP) | Éphémères « de 49151 à 65535 » | Ils commencent à **49152** |
| Slides 60-61 (TCP/UDP) | « Datagramme » TCP | En TCP on parle de **segment** (datagramme = UDP / IP) |
| Slide 61 (TCP/UDP) | ACK = n° de séquence reçu | ACK = **prochain n° de séquence attendu** (n° reçu + nombre d'octets reçus) |
| TD – schéma / table | PC-B / PC-C | Il s'agit de **PC-B** (192.168.0.3/24) |
| TD – interfaces | G0/0, G0/1 | Sur l'ISR4331 : **G0/0/0** et **G0/0/1** |

## 6. Partie 2 – ACL sur R1

**Objectif** : n'autoriser en Telnet que PC-A (192.168.1.3) et les postes d'admin réservés 192.168.1.4 à .7.

### a. Accès console et mode privilégié

Clic sur R1 → onglet **CLI** → Entrée → `Password: cisco` → `R1>` → `enable` → `Password: class` → **`R1#`**.

### b. Options de `ip access-list`

```
R1(config)# ip access-list ?
```
L'**espace avant le `?`** liste les mots qui peuvent suivre (sans espace, IOS complèterait le mot en cours). On y voit notamment `standard` et `extended`.

### c. Options de `ip access-list standard`

```
R1(config)# ip access-list standard ?
  <1-99>       Standard IP access-list number
  <1300-1999>  Standard IP access-list number (expanded range)
  WORD         Access-list name
```

### d. Créer l'ACL nommée

```
R1(config)# ip access-list standard ADMIN-MGT
R1(config-std-nacl)#
```
`std-nacl` = *standard named access control list*.

### e. Options du mode ACL

```
R1(config-std-nacl)# ?
```
`permit`, `deny`, `remark` (commentaire), numéro de séquence, `exit`...

### f. Ajouter les règles

```
R1(config-std-nacl)# permit host 192.168.1.3
R1(config-std-nacl)# permit 192.168.1.4 0.0.0.3
R1(config-std-nacl)# exit
```
- Règle 1 : un seul hôte, PC-A (`host` = wildcard 0.0.0.0).
- Règle 2 : plage .4 à .7 (wildcard 0.0.0.3, inverse de 255.255.255.252).
- Pas besoin de `deny any` : il est **implicite**.

Vérification :
```
R1# show access-lists
Standard IP access list ADMIN-MGT
    10 permit host 192.168.1.3
    20 permit 192.168.1.4 0.0.0.3
```
IOS numérote les règles automatiquement **par pas de 10**.

### g. Appliquer l'ACL aux lignes vty

```
R1(config)# line vty 0 4
R1(config-line)# access-class ADMIN-MGT in
R1(config-line)# exit
```
- `access-class` (et non `ip access-group`) : on filtre **qui peut administrer R1**, pas le trafic qui le traverse. PC-B peut toujours pinger PC-A.
- `in` : on filtre les connexions **entrantes** sur les lignes.

Vérification : `show running-config` → section `line vty 0 4` → `access-class ADMIN-MGT in`.
Sauvegarde : `copy running-config startup-config`.

## 7. Partie 3 – Vérification via Telnet

> Telnet est utilisé ici par simplicité. En production, on utilise **SSH**, car Telnet transmet tout en clair (y compris les mots de passe).

### a-c. Telnet depuis PC-A (192.168.1.3) → autorisé

```
C:\> telnet 192.168.1.1
Acces non autorise interdit !
User Access Verification
Password:            ← cisco
R1> enable
Password:            ← class
R1#
R1# exit
```
Pas de `Username:` : on n'a créé aucun compte, `login` sur les vty ne demande qu'un mot de passe.

### d-e. PC-A en 192.168.1.100 → refusé

```
C:\> telnet 192.168.1.1
Trying 192.168.1.1 ...
% Connection refused by remote host
```
- **La session a-t-elle abouti ?** Non.
- **Message reçu :** `% Connection refused by remote host`.

Le refus intervient **avant** la bannière et la demande de mot de passe : une machine non autorisée ne peut même pas tenter de deviner le mot de passe. L'adresse .100 reste dans le même réseau que R1 : on teste donc uniquement l'effet de l'ACL, sans problème de routage parasite.

### f. PC-A en 192.168.1.5 → autorisé

Adresse choisie au milieu de la plage pour prouver que la règle couvre bien tout le bloc .4–.7.
- **La session a-t-elle abouti ?** Oui.

### g. Compteurs de correspondances

```
R1# show ip access-lists
Standard IP access list ADMIN-MGT
    5 permit host 192.168.1.3 (2 match(es))
    10 permit 192.168.1.4 0.0.0.3 (2 match(es))
```
(Numérotation 5/10 due à la correction faite pendant le TD, voir section 10.)

Les tentatives refusées **n'apparaissent nulle part** : elles sont tombées sur le `deny any` implicite, qui n'a pas de compteur.

**Question : pourquoi deux correspondances pour une seule connexion ?**
> Une connexion Telnet repose sur TCP, qui établit la session en plusieurs échanges (SYN, SYN-ACK, ACK). Deux de ces segments vont du client vers le routeur (SYN et ACK). Le routeur consulte l'ACL à plus d'un moment de l'établissement, vraisemblablement à l'arrivée de la demande de connexion puis lors de sa validation, et chaque consultation incrémente le compteur. Cisco ne documente pas précisément ce comportement : c'est une hypothèse argumentée.

**Question : comment déterminer à quel moment les deux correspondances se produisent ?**
> En suivant la connexion paquet par paquet et en relevant le compteur après chaque paquet : dans Packet Tracer, avec le **mode Simulation** (filtré sur TCP/Telnet) et `show ip access-lists` entre chaque étape, après avoir remis les compteurs à zéro (`clear access-list counters`) ; sur du vrai matériel, avec une capture **Wireshark** ou les commandes `debug`.

### h. Ajouter un `deny any` explicite

```
R1(config)# ip access-list standard ADMIN-MGT
R1(config-std-nacl)# deny any
R1(config-std-nacl)# exit
```
- Le résultat du filtrage ne change pas (le deny implicite existait déjà).
- Intérêt : une ligne visible **avec un compteur** → on peut mesurer les tentatives bloquées (erreur de config, tentative d'intrusion).
- Sans numéro, la règle est ajoutée **à la fin** (plus grand numéro + 10). Placée avant les `permit`, elle bloquerait tout le monde.

### i. Telnet depuis PC-B → refusé

```
C:\> telnet 192.168.0.1
Trying 192.168.0.1 ...
% Connection refused by remote host
```
On peut viser 192.168.0.1 ou 192.168.1.1 : l'ACL est sur les **lignes vty**, elle s'applique quelle que soit l'interface d'arrivée.

### j. Compteur du `deny any`

```
R1# show ip access-lists
Standard IP access list ADMIN-MGT
    5 permit host 192.168.1.3 (2 match(es))
    10 permit 192.168.1.4 0.0.0.3 (2 match(es))
    20 deny any (4 match(es))
```
(4 correspondances observées dans Packet Tracer pour une tentative, 3 dans l'énoncé.)

**Question : pourquoi une connexion refusée génère-t-elle plus de correspondances qu'une connexion réussie ?**
> Une connexion refusée ne s'établit pas proprement : faute de réponse valide, le client TCP **retransmet** sa demande de connexion plusieurs fois avant d'abandonner (mécanisme timeout + retransmission de TCP). Chaque retransmission arrive sur le routeur, est évaluée par l'ACL et incrémente le compteur du `deny any`. Le nombre exact dépend de l'implémentation TCP du client (4 dans Packet Tracer, 3 dans l'énoncé).

## 8. Partie 4 – Défi : ACL sur S1

**Consigne** : autoriser uniquement PC-A en Telnet sur S1. ⚠️ Remettre PC-A en **192.168.1.3** avant de commencer.

### Étape 1 – Configuration

```
S1# configure terminal
! Nom choisi : fonction + équipement
S1(config)# ip access-list standard ADMIN-MGT-S1
! Seul PC-A est autorisé
S1(config-std-nacl)# permit host 192.168.1.3
! Facultatif : refus explicite pour avoir un compteur
S1(config-std-nacl)# deny any
S1(config-std-nacl)# exit
!
! TOUTES les lignes vty du switch : 0 à 15
S1(config)# line vty 0 15
S1(config-line)# access-class ADMIN-MGT-S1 in
S1(config-line)# exit
S1(config)# end
S1# copy running-config startup-config
```

**Points clés**
- **Choix du nom** : libre, en majuscules, sans espace, décrivant la fonction. `ADMIN-MGT-S1` indique fonction + équipement ; reprendre `ADMIN-MGT` sur tous les équipements serait aussi valable (même fonction, même nom). C'est la politique de nommage de l'équipe qui tranche.
- **Une seule règle `permit`** : pas de plage cette fois.
- **`line vty 0 15`** : c'est le piège du défi. Avec `0 4`, les lignes 5 à 15 resteraient **sans filtrage** : un attaquant pourrait s'y connecter une fois les premières lignes occupées.
- Le nom dans `access-class` doit être **identique caractère pour caractère** à celui de l'ACL.

### Étape 2 – Tests

| Depuis | Commande | Résultat attendu |
|---|---|---|
| PC-A (192.168.1.3) | `telnet 192.168.1.2` | Bannière + mot de passe → **accès OK** |
| PC-B (192.168.0.3) | `ping 192.168.1.2` puis `telnet 192.168.1.2` | Ping OK, Telnet **refusé** |

Le ping préalable depuis PC-B prouve que S1 est joignable (routage via R1 + `ip default-gateway` sur S1) : le refus Telnet vient donc bien de l'ACL et non d'un problème réseau.

Vérification : `show access-lists` sur S1 → correspondances sur le `permit host` et sur le `deny any`.

## 9. Questions de réflexion

### 1. De quelles façons les ACL peuvent-elles être appliquées ?

> Les ACL peuvent être appliquées **sur une interface** (`ip access-group`, en entrée ou en sortie) pour filtrer le trafic qui traverse l'équipement, ou **sur les lignes vty** (`access-class`) pour restreindre l'accès d'administration à distance. Plus largement, une ACL est un outil de **sélection de trafic** réutilisé par d'autres fonctions : NAT (adresses à traduire), QoS (trafic à prioriser), VPN (trafic à chiffrer), filtrage de routes. Dans ces cas, `permit` signifie « sélectionner » et non « laisser passer ».

### 2. Une ACL sur les lignes vty améliore-t-elle la sécurité de Telnet ? Telnet devient-il un outil d'accès distant plus viable ?

> **Elle améliore la sécurité de l'accès, pas celle du protocole.** L'ACL réduit la surface d'attaque : seules quelques adresses peuvent se connecter, les autres sont refusées avant même la demande de mot de passe, ce qui empêche les tentatives de force brute depuis le reste du réseau.
>
> En revanche, **Telnet reste non chiffré** : identifiants, mots de passe et commandes circulent en clair et peuvent être capturés par quiconque intercepte le trafic sur le chemin. De plus, une ACL standard ne vérifie que l'adresse IP source, qu'un attaquant présent sur le réseau autorisé peut utiliser ou usurper. Telnet ne devient donc **pas** un outil d'administration viable : en production, on le remplace par **SSH** (chiffré), tout en conservant l'ACL sur les vty comme couche de protection supplémentaire.

### 3. Pourquoi appliquer une ACL aux lignes vty plutôt qu'à des interfaces spécifiques ?

> Parce qu'une ACL sur les lignes vty protège **l'accès à l'équipement lui-même**, quelle que soit l'interface par laquelle la connexion arrive. Un routeur possède plusieurs interfaces et donc plusieurs adresses (dans le TD, R1 est joignable en 192.168.0.1 comme en 192.168.1.1) : une seule ACL sur les vty les couvre toutes, y compris les interfaces ajoutées plus tard.
>
> Avec des ACL d'interface, il faudrait des ACL **étendues** (pour cibler le port Telnet/SSH et l'adresse du routeur) sur **chaque** interface, dans le bon sens, avec un risque d'oubli et d'effets de bord : une ACL d'interface filtre aussi le trafic qui traverse le routeur, alors qu'on veut seulement contrôler l'administration. L'ACL vty est donc plus simple, plus ciblée et plus facile à maintenir.

## 10. Dépannage rencontré pendant le TD

| Symptôme | Cause | Solution |
|---|---|---|
| `%Error parsing filename (Bad file number)` après un collage | En collant un bloc, la ligne suivant `copy running-config startup-config` a été lue comme **réponse** à `Destination filename [startup-config]?` → config non sauvegardée | Coller les blocs jusqu'à `end`, puis taper **à la main** `copy running-config startup-config` et valider par Entrée |
| Sortie de `show ip interface brief` coupée sur S1 | Pagination `--More--` | Appuyer sur **Espace** pour afficher la suite |
| Telnet refusé depuis PC-A (192.168.1.3), sans bannière ni mot de passe | La règle `permit host 192.168.1.3` **manquait** : `show access-lists` ne montrait que la plage .4–.7 | Insertion avec un numéro de séquence inférieur : `5 permit host 192.168.1.3` dans `ip access-list standard ADMIN-MGT` |
| ACL vide `ADMIN-MGY` visible dans `show ip access-lists` | **Faute de frappe** dans le nom : `ip access-list standard ADMIN-MGY` a créé une nouvelle ACL au lieu d'entrer dans l'existante (cause probable de la règle manquante) | `no ip access-list standard ADMIN-MGY` |

**Leçons**
- `Connection refused` **sans bannière** = refus par l'ACL (ou config vty) avant l'authentification.
- Toujours vérifier avec `show access-lists` **après** avoir saisi des règles, pas seulement l'invite.
- Les noms d'ACL sont **sensibles à la casse et aux caractères** : `ADMIN-MGT`, `ADMIN_MGT`, `admin-mgt` et `ADMIN-MGY` sont quatre ACL différentes.
- L'insertion par numéro de séquence est un avantage majeur des ACL nommées.

## 11. Aide-mémoire des commandes

| Objectif | Commande | Mode |
|---|---|---|
| Voir toutes les ACL et leurs compteurs | `show access-lists` | `#` |
| Voir les ACL IP uniquement | `show ip access-lists` | `#` |
| Remettre les compteurs à zéro | `clear access-list counters` | `#` |
| Voir où une ACL est appliquée | `show running-config` (sections `interface` / `line vty`) | `#` |
| Créer une ACL standard nommée | `ip access-list standard NOM` | `(config)#` |
| Créer une ACL étendue nommée | `ip access-list extended NOM` | `(config)#` |
| Règle numérotée classique | `access-list N permit\|deny SOURCE WILDCARD` | `(config)#` |
| Autoriser un hôte | `permit host A.B.C.D` | `(config-std-nacl)#` |
| Autoriser un réseau | `permit A.B.C.D WILDCARD` | `(config-std-nacl)#` |
| Tout refuser (explicite) | `deny any` | `(config-std-nacl)#` |
| Insérer à une position | `N permit ...` | `(config-std-nacl)#` |
| Supprimer une règle | `no N` | `(config-std-nacl)#` |
| Commenter une ACL | `remark texte` | `(config-std-nacl)#` |
| Appliquer sur une interface | `ip access-group NOM in\|out` | `(config-if)#` |
| Appliquer sur les vty | `access-class NOM in` | `(config-line)#` |
| Supprimer une ACL nommée | `no ip access-list standard NOM` | `(config)#` |
| Supprimer une ACL numérotée | `no access-list N` | `(config)#` |
| Sauvegarder | `copy running-config startup-config` | `#` |
