Introduction — à propos de l'AZ-900

L'examen AZ-900 (Microsoft Azure Fundamentals) valide une compréhension générale du cloud computing et des grandes familles de services Azure. Il ne demande pas une maîtrise technique approfondie : il vérifie que vous savez reconnaître le bon service pour un scénario donné, expliquer une différence entre deux notions proches, et situer un concept dans la bonne catégorie.

Gestion & gouvernance30–35 %Coûts, SLA, gouvernance, monitoring, outils de déploiement.

Ce document reprend et développe l'intégralité du support de formation « AZ-900 — Microsoft Azure Fundamentals » de BizzDev SA, organisé en dix modules qui suivent la même progression que le support original. Chaque notion est expliquée, illustrée par un exemple concret et accompagnée, quand c'est utile, d'un point d'attention pour l'examen.

À retenir

Pour AZ-900, la difficulté vient rarement du calcul : elle vient du vocabulaire. Le meilleur réflexe consiste à toujours relier une notion à un scénario concret plutôt qu'à l'apprendre isolément.

Module 01

Concepts cloud

≈ 25–30 % de l'examen

Objectif du module : acquérir le vocabulaire indispensable avant de parler des services Azure eux-mêmes. Cette base conceptuelle conditionne la compréhension de tous les modules suivants.

1.1 Le cloud computing en une phrase

Le cloud computing consiste à louer de l'informatique à la demande au lieu de tout acheter et exploiter soi-même. Concrètement, cela repose sur quatre idées combinées :

  • À la demande — une ressource (machine virtuelle, base de données, espace de stockage) se crée en quelques minutes, sans délai de commande ni d'installation physique.
  • Paiement à l'usage — la facture reflète ce qui a réellement été consommé : temps d'exécution, volume de stockage, transfert de données, options choisies.
  • Échelle mondiale — les services peuvent être déployés dans des régions proches des utilisateurs finaux, où que ceux-ci se trouvent.
  • Responsabilité partagée — Microsoft gère une partie de la pile technique, le client garde la responsabilité d'une autre partie (les données, les identités, la configuration).
Explication simple

Le cloud fonctionne comme un catalogue de services informatiques. Au lieu d'acheter un serveur, d'attendre sa livraison puis de l'installer, vous demandez une ressource dans Azure : elle apparaît en quelques minutes, avec une capacité, un prix et des options.

Exemple concret

Une entreprise veut tester une application pendant deux semaines. Avec Azure, elle peut créer une VM ou un App Service, tester, puis supprimer la ressource. Elle évite ainsi d'acheter un serveur qui resterait ensuite inutilisé.

Ce que vous devez retenir pour AZ-900

Azure fournit des ressources à la demande. Vous gagnez en rapidité et en flexibilité, mais vous devez toujours configurer, sécuriser et suivre les coûts : le cloud change le modèle de consommation, pas les responsabilités de base.

Exemple concret : une boutique en ligne doit absorber le pic du Black Friday. Le cloud permet d'augmenter rapidement la capacité pendant le pic, puis de la réduire ensuite, ce qui évite de payer toute l'année pour une capacité qui ne sert que quelques jours.

1.5 CapEx et OpEx

Une notion financière clé pour l'examen : faut-il acheter des actifs (CapEx) ou payer l'usage (OpEx) ?

CapEx — dépense d'investissementOpEx — dépense opérationnelle
Achat initial important, souvent lourdPaiement régulier selon la consommation
Matériel amorti sur plusieurs annéesPlus facile de démarrer petit et d'ajuster
Risque de surcapacité ou de sous-capacitéAjustement rapide des ressources selon le besoin
Décisions plus difficiles à corriger une fois l'achat faitFactures à surveiller pour éviter les mauvaises surprises
Explication simple

CapEx signifie acheter un actif avant de l'utiliser : serveurs, stockage, salle machine. OpEx signifie payer une dépense d'exploitation, souvent mensuelle ou liée à l'usage. Le cloud favorise plutôt le modèle OpEx.

Exemple concret

Un datacenter classique impose d'acheter suffisamment de serveurs pour couvrir le pic futur. Dans Azure, on peut démarrer petit, augmenter la taille si l'application grandit, puis réduire ou arrêter les ressources devenues inutiles.

À retenir

Le cloud ne supprime pas le coût ; il le transforme. On passe d'un investissement initial lourd (CapEx) à une dépense plus variable et pilotable dans le temps (OpEx).

1.7 IaaS, PaaS, SaaS

Plus un service est managé par Microsoft, moins vous devez administrer les couches basses — et inversement, plus vous gardez de contrôle, plus vous assumez de responsabilités.

Sur site
100 % vous
IaaS
OS, apps, données
PaaS
Apps, données
SaaS
Comptes, accès
Géré par vous Géré par Microsoft
Explication simple

Une analogie utile est celle du restaurant. IaaS ressemble à louer une cuisine vide : vous avez beaucoup de contrôle, mais vous gérez beaucoup de choses vous-même. PaaS ressemble à une cuisine déjà équipée : vous cuisinez, mais l'infrastructure est prête. SaaS ressemble à commander un plat : l'application est déjà fournie, prête à consommer.

Exemple concret

Une VM Azure est de l'IaaS : vous gérez l'OS. Azure App Service est du PaaS : vous déployez votre code sans gérer le serveur sous-jacent. Microsoft 365 est du SaaS : vous utilisez directement l'application, sans rien installer ni administrer.

Ce que vous devez retenir pour AZ-900

Plus on va vers le SaaS, moins vous gérez de couches techniques. Plus on va vers l'IaaS, plus vous contrôlez, mais plus vous êtes responsable de la maintenance et de la sécurité.

1.8 Responsabilité partagée

La question à toujours se poser face à un service Azure est : qui est responsable de quoi ?

  • Toujours côté client — les données, les comptes, les identités, les terminaux et les décisions de configuration.
  • Toujours côté Microsoft — la sécurité physique des datacenters et l'infrastructure cloud globale.
  • Variable selon IaaS / PaaS / SaaS — le système d'exploitation, le middleware, le réseau et le runtime changent de responsable selon le modèle de service utilisé.
Explication simple

Dans Azure, la répartition des responsabilités dépend du type de service. Microsoft gère toujours les datacenters physiques. Le client garde toujours la responsabilité de ses données, de ses comptes, de ses identités et de ses choix de configuration.

Exemple concret

Si vous créez une VM, vous devez gérer les mises à jour du système d'exploitation invité. Si vous utilisez App Service, Azure prend davantage en charge la plateforme. Mais dans les deux cas, une permission RBAC mal configurée reste de votre responsabilité.

À retenir

Plus le service est managé, plus Microsoft prend en charge l'exploitation technique. En revanche, les données, les identités et les droits d'accès restent toujours à surveiller côté client, quel que soit le modèle choisi.

Module 02

Architecture Azure

≈ 35–40 % de l'examen (bloc architecture)

Objectif du module : comprendre l'organisation globale d'Azure — régions, subscriptions, resource groups — pour savoir où et comment se situe chaque ressource.

2.1 Régions Azure

Une région est une zone géographique contenant un ou plusieurs datacenters Azure. Le choix d'une région influence la latence, la résidence des données, la disponibilité de certains services et souvent le prix.

  • Régions jumelées — certaines régions sont associées deux à deux pour faciliter la continuité d'activité et la reprise après sinistre.
  • Régions souveraines — environnements dédiés répondant à des contraintes gouvernementales ou réglementaires spécifiques.
  • Réflexe examen — tous les services Azure ne sont pas disponibles dans toutes les régions.
Explication simple

Une région est un emplacement géographique Azure. Une zone de disponibilité est une séparation physique à l'intérieur d'une région. Une paire de régions aide certains scénarios de continuité et de reprise après sinistre.

Exemple concret

Déployer en France Central peut réduire la latence pour des utilisateurs français. Utiliser plusieurs zones de disponibilité protège mieux contre une panne locale à l'intérieur de la région choisie.

À retenir

Une région rapproche l'application des utilisateurs, aide à respecter certaines contraintes de localisation des données, et améliore la résilience globale de l'architecture.

2.2 Zones de disponibilité

Une zone de disponibilité isole les pannes physiques à l'intérieur d'une même région : un datacenter ou un groupe de datacenters physiquement indépendant, protégeant contre une panne locale d'alimentation, de réseau ou de refroidissement.

  • Services zonaux — déployés dans une zone précise, choisie explicitement.
  • Services redondants interzones — répliqués automatiquement entre plusieurs zones pour une meilleure résilience.

2.3 Hiérarchie Azure

Il est indispensable de savoir replacer une ressource au bon niveau de la hiérarchie Azure, car cette structure conditionne la facturation, les droits d'accès et les règles de gouvernance applicables.

Management groupRegroupe plusieurs subscriptions pour appliquer une gouvernance à grande échelle.
SubscriptionUnité de facturation, de limites et de gestion des accès.
Resource groupConteneur logique pour des ressources qui partagent un cycle de vie commun.
ResourceL'élément concret lui-même : VM, storage account, VNet, base de données, etc.
À retenir

Retenez bien l'enchaînement management groups → subscriptions → resource groups → resources. C'est la base pour comprendre les scopes de gouvernance dans Azure.

2.4 Pourquoi cette hiérarchie compte : la notion de scope

Un scope est le niveau auquel on applique une règle ou un droit. Plus on applique une règle haut dans la hiérarchie, plus son effet couvre d'éléments. Ce principe est vrai pour les rôles RBAC, les policies de gouvernance, et certains contrôles de coûts.

Explication simple

Un scope est le niveau auquel on applique une règle ou un droit. Plus on applique haut, plus l'effet couvre d'éléments — c'est vrai pour les rôles RBAC, les policies et certains contrôles de gouvernance.

Exemple concret

Donner le rôle Reader sur une subscription entière permet de lire beaucoup de ressources en une seule attribution. Donner le même rôle sur un seul resource group limite l'accès à ce groupe uniquement.

Ce que vous devez retenir pour AZ-900

Pensez toujours à trois questions : quelle identité reçoit le droit, quel rôle lui est attribué, et à quel niveau ?

2.5 Bon usage des resource groups

  • Regroupez les ressources qui « vivent ensemble » — qui doivent être créées, modifiées et supprimées en même temps.
  • Un resource group appartient à une seule région pour ses métadonnées, mais les ressources qu'il contient peuvent être physiquement situées dans des régions différentes.
  • Attention : supprimer un resource group supprime toutes les ressources qu'il contient.

2.6 Subscriptions et management groups

SubscriptionManagement group
Unité de facturation et de quotasRegroupe plusieurs subscriptions
RBAC et policies applicables directementPermet d'appliquer politiques et accès à grande échelle
Séparation par environnement, équipe, application ou budgetParticulièrement utile dans les grandes organisations

2.7 Azure Resource Manager (ARM)

ARM est la couche de gestion unique qui reçoit toutes les demandes de création, de modification ou de suppression de ressources — quel que soit l'outil d'origine : portail, ligne de commande, PowerShell, SDK ou template.

  • Le portail, la CLI, PowerShell, les SDK et les templates passent tous par ARM.
  • Des déploiements déclaratifs sont possibles avec des ARM templates (JSON) ou avec Bicep, un langage plus lisible qui se compile en ARM template.
  • ARM assure une gestion cohérente : tags, RBAC, verrous (locks), policies.
  • Point important : ARM gère les ressources, pas directement le contenu applicatif qui tourne dessus.
À retenir

ARM est la couche de contrôle unifiée. Peu importe l'outil utilisé, les opérations passent par le même moteur de déploiement et de gestion.

Module 03

Services Azure : Compute

≈ 35–40 % de l'examen (bloc architecture)

Objectif du module : héberger du code, des applications, des conteneurs et des postes de travail virtuels. Le compute désigne la capacité de calcul nécessaire à l'exécution d'une charge de travail.

3.1 Vue d'ensemble des services compute

Virtual Machines

Contrôle élevé, mais responsabilité élevée : vous gérez l'OS et tout ce qui en dépend.

App Service

Hébergement web/API managé, idéal pour les applications web classiques.

Container Instances (ACI)

Packaging portable, simple, peu d'orchestration.

Azure Kubernetes Service (AKS)

Orchestration à grande échelle pour les microservices.

Azure Functions

Modèle serverless événementiel : exécuter du code à la demande, sans gérer de serveur.

Azure Virtual Desktop

Virtualisation de postes de travail et d'applications, accessibles à distance.

Explication simple

Tous les services compute exécutent du code ou des applications. La différence principale porte sur ce que vous voulez gérer vous-même : un OS complet, une plateforme web déjà prête, un conteneur, ou une simple fonction déclenchée par un événement.

Exemple concret

Une vieille application Windows difficile à modifier ira souvent sur une VM. Une API web moderne ira souvent sur App Service. Un traitement déclenché par l'upload d'un fichier peut aller sur Azure Functions.

À retenir

Le bon service compute dépend d'un arbitrage simple : contrôle maximal (VM), simplicité managée (App Service), événementiel (Functions), portabilité conteneurs (ACI / AKS).

3.2 Virtual Machines vs App Service

Azure Virtual MachinesAzure App Service
Vous choisissez l'OS, la taille, les disques, le réseauPlateforme web managée
Bon pour le lift-and-shift ou les logiciels nécessitant un accès OSDéployer du code sans gérer de serveur
Vous gérez le patching et la configuration de l'OSMise à l'échelle, slots de déploiement, certificats, CI/CD intégrés

Pour les machines virtuelles, quelques notions reviennent systématiquement à l'examen : la taille de VM détermine le CPU, la RAM, le disque temporaire et la capacité réseau disponibles ; les images constituent la base de départ (Windows, Linux ou image personnalisée) ; les availability sets et les zones de disponibilité réduisent le risque de panne simultanée ; les scale sets gèrent un groupe de VM identiques avec mise à l'échelle automatique.

3.3 Serverless avec Azure Functions

  • Déclencheur — HTTP, minuteur, file d'attente, événement, etc.
  • Facturation — souvent liée aux exécutions et à leur durée.
  • Cas d'usage — traitement court, automatisation, intégration, tâches événementielles.
  • Limite conceptuelle — pas idéal pour des processus longs nécessitant un contrôle serveur complet.

3.4 Comment choisir un service compute ?

  • Besoin d'un accès OS complet ? → Virtual Machine
  • Application web/API standard ? → App Service
  • Exécution courte déclenchée par un événement ? → Functions
  • Besoin de conteneurs, simple et peu d'orchestration ? → Azure Container Instances
  • Architecture microservices ou cluster orchestré ? → Azure Kubernetes Service

3.5 Containers : ACI vs AKS

Azure Container InstancesAzure Kubernetes Service
Lancer rapidement un conteneur, peu d'orchestrationOrchestration de clusters Kubernetes managée
Bon pour des tâches simples ou temporairesAdapté aux microservices et aux workloads complexes
Simple à mettre en œuvrePlus puissant, mais nécessite des connaissances Kubernetes

3.6 Azure Virtual Desktop

Azure Virtual Desktop virtualise le poste de travail ou les applications, rendant un bureau ou des applications distantes accessibles aux utilisateurs. Ce service est utile pour le télétravail, les prestataires externes ou les environnements standardisés. Il s'appuie sur l'identité, le réseau, le stockage de profils et la sécurité.

Module 04

Réseau Azure

≈ 35–40 % de l'examen (bloc architecture)

Objectif du module : relier, isoler, filtrer et exposer les services correctement. Le réseau est souvent le domaine le plus dense en acronymes de l'AZ-900.

4.1 Virtual Network (VNet)

Le VNet est le réseau privé logique dans Azure. Il sert à isoler, découper et connecter les ressources tout en maîtrisant le trafic.

  • Adressage IP — définir un espace d'adresses privé pour le réseau virtuel.
  • Subnets — découper le réseau par rôle ou par zone de sécurité.
  • Routage — contrôler les chemins réseau si nécessaire.
  • Connexion — peering entre VNets, VPN Gateway ou ExpressRoute pour relier des réseaux entre eux.
Explication simple

Un VNet ressemble à un réseau d'entreprise, mais défini dans Azure. On y place des ressources, on le découpe en subnets et on contrôle les communications avec des règles de sécurité.

Exemple concret

Vous pouvez placer des VM dans un subnet « web » et une base de données dans un subnet plus protégé. Les NSG filtrent alors les flux autorisés, par exemple HTTP/HTTPS ou RDP.

Ce que vous devez retenir pour AZ-900

VNet = isolation et connectivité ; subnet = découpage interne ; NSG = filtrage réseau simple.

4.2 Services réseau à connaître

VPN Gateway

Connexion chiffrée via Internet — plus rapide à mettre en place, dépend de la qualité de la connexion.

ExpressRoute

Connexion privée via un fournisseur opérateur — plus prévisible en performance et latence.

Network Security Group

Filtrage réseau par règles de source, destination et port.

Azure Firewall

Pare-feu managé centralisé, plus riche qu'un NSG.

DDoS Protection

Protection contre les attaques volumétriques par saturation.

Application Gateway / WAF

Répartition applicative HTTP(S) avec protection contre les attaques web courantes.

4.3 Load Balancer vs Application Gateway

Une confusion classique à l'examen : ne pas mélanger couche réseau et couche applicative.

Azure Load BalancerApplication Gateway
Répartition de charge de couche 4 (TCP/UDP)Répartition de couche 7 (HTTP/HTTPS)
Scénarios simples, internes ou externesRoutage possible par URL ou par nom d'hôte
Ne comprend pas le contenu applicatifPeut intégrer un WAF pour la protection web

4.4 DNS et livraison globale

  • Azure DNS — héberger et gérer des zones DNS.
  • Azure Front Door — entrée globale pour applications web, avec accélération et sécurité intégrées.
  • Traffic Manager — routage DNS selon la performance, la priorité ou la géographie.
  • CDN — cache de contenu statique placé près des utilisateurs pour réduire la latence.

4.5 Schéma — chemin d'une application web Azure

Un scénario typique : l'utilisateur passe d'abord par le DNS ou Front Door, qui oriente sa requête vers le point d'entrée de l'application ; l'Application Gateway (avec son WAF) protège ensuite le trafic HTTP(S) ; le service applicatif (App Service ou VM) traite la requête, puis dialogue avec la base de données.

À retenir

Le DNS oriente l'utilisateur vers l'entrée de l'application, le WAF protège le trafic HTTP(S), et le service applicatif traite la requête avant de dialoguer avec la base de données.

Module 05

Stockage et données

≈ 35–40 % de l'examen (bloc architecture)

Objectif du module : comprendre les grands types de stockage, la redondance et les bases de données Azure.

5.1 Azure Storage : les quatre familles

Blob Storage

Objets non structurés : images, logs, sauvegardes, documents.

Azure Files

Partages de fichiers managés, compatibles SMB/NFS.

Queue Storage

Messages simples pour découpler des composants applicatifs.

Table Storage

Stockage NoSQL clé/valeur simple.

Explication simple

Blob stocke des objets (images, vidéos, sauvegardes, logs). Files expose un partage de fichiers. Queues transporte des messages entre applications. Tables stocke des données NoSQL simples.

Exemple concret

Pour stocker des factures PDF, on utilise Blob. Pour remplacer un partage réseau SMB, on utilise Azure Files. Pour découpler deux composants applicatifs, on utilise une Queue.

Ce que vous devez retenir pour AZ-900

La question AZ-900 cache souvent la réponse dans le type de donnée : objet, fichier partagé, message ou table clé-valeur.

5.2 Blob tiers : Hot, Cool, Archive

HotCool / Archive
Données consultées souventCool : accès moins fréquent
Coût de stockage plus élevéArchive : conservation longue, restauration plus lente
Coût d'accès plus faibleUtiles pour les logs, sauvegardes et besoins de conformité

5.3 Redondance du stockage

  • LRS — copies dans un seul datacenter, dans une région locale.
  • ZRS — copies synchrones réparties dans plusieurs zones d'une même région.
  • GRS / GZRS — réplication vers une région secondaire distante.
  • RA-GRS — lecture possible depuis la région secondaire, en plus de la réplication géographique.
À retenir

La redondance répond au niveau de protection attendu. Plus on souhaite de résilience géographique ou zonale, plus le coût et la complexité peuvent augmenter.

5.4 Azure Disk Storage

Les disques servent principalement aux machines virtuelles. Les disques managés déchargent l'administration du compte de stockage sous-jacent. Plusieurs types existent selon la performance recherchée : Standard HDD/SSD, Premium SSD ou Ultra Disk. Les snapshots permettent de capturer un état ponctuel d'un disque, pour la sauvegarde ou le clonage.

5.5 Migration et transfert de données

  • AzCopy — copie en ligne de données vers ou depuis Azure Storage.

5.7 Relationnel ou NoSQL ?

RelationnelNoSQL
Tables, lignes, colonnes, schéma structuréDocuments, clé/valeur, graphe ou colonnes selon le moteur

Explication simple

Une base relationnelle organise les données en tables avec des relations et du SQL. Une base NoSQL est plus flexible et convient mieux à des données semi-structurées, très distribuées ou à grande échelle.

Exemple concret

Une application de gestion commerciale avec clients, commandes et factures ira souvent vers Azure SQL. Une application mondiale manipulant des documents JSON avec une exigence de faible latence peut aller vers Cosmos DB.

Ce que vous devez retenir pour AZ-900

Ne choisissez pas Cosmos DB juste parce que c'est moderne : choisissez selon le besoin de modèle de données, de distribution géographique, de performance et de scalabilité.

Module 06

Identité, accès et sécurité

≈ 30–35 % de l'examen (bloc gouvernance)

Objectif du module : dans Azure, l'identité est devenue le nouveau périmètre de sécurité.

6.1 Microsoft Entra ID

Microsoft Entra ID est le service d'identité cloud utilisé pour authentifier utilisateurs, applications et appareils.

  • Annuaire cloud — utilisateurs, groupes, applications, appareils.
  • SSO — une seule identité pour accéder à plusieurs applications.
  • MFA — ajout d'un facteur d'authentification supplémentaire pour réduire le risque de compromission.
  • Identités externes — inviter des partenaires ou des clients selon les besoins.
Explication simple

Microsoft Entra ID authentifie les utilisateurs, groupes, applications et appareils. Il permet le SSO, le MFA et s'intègre avec de nombreux services Azure et SaaS.

Exemple concret

Un administrateur se connecte au portail Azure via Entra ID. Une application peut aussi utiliser une identité pour accéder à Key Vault ou à Storage sans jamais stocker de mot de passe en dur.

À retenir

Entra ID répond à « qui se connecte ? », tandis que RBAC répond à « que peut faire cette identité ? ». Retenez bien cette séparation des rôles.

6.2 Authentification vs autorisation

AuthentificationAutorisation
Prouver qui vous êtesDéterminer ce que vous pouvez faire
Mot de passe, MFA, certificat, connexion sans mot de passeRôles, permissions, scopes
Question : « Qui est l'utilisateur ? »Question : « A-t-il le droit de faire cette action ? »

6.3 RBAC (Role-Based Access Control)

  • Security principal — utilisateur, groupe, service principal ou managed identity.
  • Role definition — ensemble de permissions : Reader, Contributor, Owner, etc.
  • Scope — management group, subscription, resource group ou ressource individuelle.
  • Réflexe examen — toujours accorder le minimum nécessaire : principe du moindre privilège (least privilege).
Explication simple

RBAC attribue un rôle à une identité sur un niveau précis. Le rôle contient les permissions, et le scope limite l'endroit où ces permissions s'appliquent.

Exemple concret

Si le groupe « Support » reçoit le rôle Reader sur un resource group, il peut voir les ressources de ce groupe mais ne peut pas les modifier. S'il reçoit le rôle Contributor, il peut modifier beaucoup plus de choses.

Ce que vous devez retenir pour AZ-900

Principe important : least privilege. La formule à retenir : identité + rôle + scope = autorisation effective.

6.4 Managed identities

Une managed identity évite de stocker des secrets dans le code. Elle est attribuée à une ressource Azure — une VM, une Function, un App Service — et Azure gère automatiquement les identifiants associés. Elle permet d'accéder à Key Vault, à Storage ou à d'autres services via Entra ID, réduisant ainsi le risque lié aux mots de passe et aux clés présents dans les fichiers de configuration.

6.5 Microsoft Defender for Cloud

  • Secure Score — mesure la posture de sécurité et propose des recommandations pour l'améliorer.
  • Recommandations — actions concrètes sur des ressources mal configurées.
  • Protection des workloads — plans de protection pour serveurs, stockage, conteneurs, bases de données.
  • Vue centralisée — permet de prioriser les risques de sécurité.

6.6 Key Vault

  • Secrets — mots de passe, chaînes de connexion, clés API.
  • Keys — clés de chiffrement utilisées par les applications ou les services.
  • Certificates — gestion et rotation de certificats.
  • Bon réflexe — ne jamais placer un secret en clair dans le code.
Explication simple

Un secret est une information sensible : mot de passe, chaîne de connexion, clé API. Key Vault sert à centraliser, protéger, auditer et parfois faire tourner ces secrets.

Exemple concret

Une Azure Function peut utiliser une managed identity pour lire un secret dans Key Vault. Le code de l'application ne contient donc jamais le mot de passe de la base de données.

Ce que vous devez retenir pour AZ-900

Réflexe examen : dès qu'une question évoque des secrets, des clés ou des certificats, pensez Key Vault.

6.7 Sécurité réseau : NSG, Firewall, WAF

NSGFirewall / WAF

Règles de ports, protocoles et adresses IPWAF : protège les applications web contre les attaques courantes

6.8 Schéma — identité, authentification et accès

Un même scénario permet de distinguer clairement Entra ID, MFA, token et RBAC : un utilisateur ou une application se présente à Microsoft Entra ID ; le MFA renforce l'étape de connexion ; une fois l'identité validée, un token est émis ; RBAC s'applique ensuite pour décider si cette identité peut lire, modifier ou supprimer la ressource Azure demandée.

À retenir

Entra ID répond à « qui se connecte ? », tandis que RBAC répond à « que peut faire cette identité ? ».

Module 07

Gouvernance et conformité

≈ 30–35 % de l'examen (bloc gouvernance)

Objectif du module : mettre en place des garde-fous avant que l'environnement Azure ne devienne incontrôlable. La gouvernance répond globalement à une question : qui peut faire quoi, où, comment, et à quel coût ?

7.1 L'idée générale de la gouvernance Azure

  • Organisation — management groups, subscriptions, resource groups.
  • Accès — RBAC, groupes, séparation des rôles.
  • Règles — Azure Policy et initiatives.
  • Traçabilité — tags, logs, audit et conformité.

7.2 Azure Policy

  • Exemples — interdire une région, exiger un tag, limiter les tailles de VM autorisées.
  • Audit ou Deny — observer une configuration non conforme, ou carrément bloquer sa création.
  • Initiatives — regrouper plusieurs policies dans un même ensemble.
  • Différence avec RBAC — RBAC donne le droit d'agir ; Policy contrôle ce qui est autorisé.
Explication simple

RBAC dit si une personne a le droit de créer une ressource. Azure Policy dit si la ressource respecte les règles de l'organisation : région autorisée, tags obligatoires, SKU interdits, etc.

Exemple concret

Un utilisateur Contributor peut avoir le droit de créer une VM, mais une policy peut bloquer cette création si la région choisie n'est pas approuvée par l'organisation.

Ce que vous devez retenir pour AZ-900

Phrase à mémoriser : RBAC contrôle les actions ; Policy contrôle les propriétés et la conformité des ressources.

7.3 RBAC vs Azure Policy

RBACAzure Policy
Contrôle les actions des identitésContrôle les propriétés des ressources
Exemple : Alice peut créer une VMExemple : les VM ne sont autorisées qu'en Europe Ouest
Question : « Qui a le droit ? »Question : « Qu'est-ce qui est conforme ? »

7.4 Resource locks et tags

  • Locks — empêchent la suppression ou la modification accidentelle d'une ressource.
  • CanNotDelete — la ressource peut être lue et modifiée, mais pas supprimée.
  • ReadOnly — empêche toute modification de la ressource.
  • Tags — métadonnées attachées aux ressources pour le suivi des coûts, du propriétaire, de l'environnement ou de la criticité.

7.5 Conformité, confidentialité, confiance

  • Microsoft Purview — gouvernance, protection et conformité des données.
  • Service Trust Portal — documentation de conformité, rapports et ressources de confiance.
  • Compliance Manager — aide à évaluer et à améliorer la posture de conformité.
  • Attention — la conformité reste une responsabilité partagée entre Microsoft et le client.

7.6 Schéma — les garde-fous de gouvernance

Chaque outil de gouvernance répond à un besoin différent, mais complémentaire des autres : RBAC répond à « qui peut agir ? » ; Policy répond à « qu'est-ce qui est autorisé ? » ; les locks répondent à « qu'est-ce qu'on protège ? » ; les tags répondent à « comment classer et suivre le parc de ressources ? ».

À retenir

Policy sert à faire respecter des règles sur les ressources : c'est un outil de normalisation et de conformité, pas un outil d'authentification.

Module 08

Coûts, SLA et support

≈ 30–35 % de l'examen (bloc gouvernance)

Objectif du module : comprendre comment Azure facture les ressources et comment éviter les mauvaises surprises budgétaires.

8.1 Les facteurs de coût Azure

  • Type de ressource — VM, stockage, base de données, réseau, service managé.
  • Région — le prix peut varier selon l'emplacement géographique choisi.
  • Consommation — temps d'exécution, capacité, opérations, transfert de données.
  • Options — redondance, niveau de performance, support, licences, réservations.
Explication simple

Le prix dépend du service, de la taille, de la région, du temps d'exécution, du stockage, des opérations et parfois du trafic réseau. Deux ressources portant le même nom peuvent coûter très différemment selon leur SKU.

Exemple concret

Une VM coûte selon sa taille et sa durée d'allumage. Le stockage coûte selon le volume, le niveau d'accès et la redondance. Une base managée coûte selon la performance et les options choisies.

À retenir

En Azure, le prix dépend presque toujours de plusieurs curseurs combinés : taille, durée, région, performance, redondance et trafic.

8.2 Outils de prévision et de suivi des coûts

  • Pricing Calculator — estimer un coût avant le déploiement.
  • TCO Calculator — comparer le coût d'une infrastructure locale à celui d'une migration vers Azure.
  • Cost Management — suivre les dépenses réelles, les budgets, les alertes et les recommandations.
  • Azure Advisor — recommandations de coût, performance, fiabilité, sécurité et excellence opérationnelle.

8.3 Réduire les coûts

Avant déploiementAprès déploiement
Choisir la bonne taille, la bonne région, le bon SKUArrêter les ressources inutilisées
Utiliser la calculatrice de prixRedimensionner les ressources sous-utilisées
Prévoir des tags pour la refacturation interneBudgets, alertes, réservations, Azure Hybrid Benefit si éligible

8.4 SLA et disponibilité

Un SLA (Service Level Agreement) est un engagement de disponibilité d'un service, souvent exprimé en pourcentage.

SLAIndisponibilité maximale approximative par mois
99 %Environ 7 h 18 min
99,9 %Environ 43 min
99,95 %Environ 22 min
99,99 %Environ 4 min

Important : un SLA n'est pas une garantie « magique ». Pour améliorer la disponibilité réelle, on conçoit généralement l'architecture avec de la redondance, plusieurs zones ou plusieurs composants indépendants.

À retenir

Un SLA exprime un engagement de service, mais la disponibilité réelle dépend aussi de la conception de l'architecture.

8.5 Cycles de vie et support

  • Preview — fonctionnalité en préversion, pas toujours couverte comme un service General Availability.
  • General Availability — service officiellement disponible pour la production.
  • Support plans — différents niveaux de support selon les besoins de l'entreprise.
  • Status page — permet de consulter l'état des services Azure en cas d'incident.

8.6 Atelier — Estimer un coût

  • 1. Définir une petite application : composant web, base de données et stockage.
  • 2. Lister les ressources facturables.
  • 3. Repérer les paramètres qui influencent le prix (taille, région, redondance…).
  • 4. Prévoir un budget et une alerte de dépassement.
  • 5. Identifier au moins une optimisation possible.

9.1 Outils pour gérer Azure

  • Azure Portal — interface web graphique pour découvrir et administrer les ressources.

  • Serveurs hybrides — gérer des serveurs on-premises ou multi-cloud.
  • Kubernetes — appliquer une gouvernance et une configuration cohérentes.
  • Données — certains services de données Azure deviennent disponibles dans des environnements hybrides.
  • Idée clé — Azure devient un plan de contrôle, pas seulement un hébergeur de ressources.

9.4 Azure Monitor

  • Metrics — valeurs numériques mesurées dans le temps : CPU, requêtes, latence.
  • Logs — données détaillées et interrogeables, souvent via Log Analytics.
  • Alerts — notifier ou déclencher une action automatiquement quand une condition est remplie.
  • Dashboards / Workbooks — visualiser l'état général des services.
Explication simple

Une métrique est une valeur numérique dans le temps : CPU, mémoire, requêtes. Un log est un événement détaillé. Une alerte surveille une condition et prévient ou déclenche une action.

Exemple concret

Si une application est lente, les métriques montrent peut-être une hausse de latence. Les logs montrent les erreurs ou les dépendances défaillantes. L'alerte prévient l'équipe dès que le seuil est dépassé.

Ce que vous devez retenir pour AZ-900

Pour AZ-900 : métriques = mesures ; logs = détails ; alertes = notification ou action.

9.5 Log Analytics et Application Insights

  • Log Analytics workspace — centralise et interroge des logs avec le langage KQL.
  • Application Insights — observabilité applicative : requêtes, exceptions, dépendances, performance.
  • Cas d'usage — comprendre pourquoi une application est lente ou en erreur.
  • Réflexe examen — le monitoring technique n'est pas la même chose que la gouvernance des coûts.

9.6 Azure Advisor et Service Health

  • Azure Advisor — recommandations personnalisées de coût, sécurité, fiabilité et performance.
  • Azure Service Health — incidents Azure qui affectent vos ressources.
  • Resource Health — état de santé d'une ressource spécifique.
  • Action Groups — destinataires et actions déclenchés par les alertes.

9.7 Schéma — pipeline de monitoring

Le monitoring transforme des signaux techniques bruts en information exploitable : les ressources et applications génèrent des métriques, des logs et des traces ; Azure Monitor les collecte ; Log Analytics permet de les interroger ; des alertes ou des workbooks sont produits ; ceux-ci déclenchent des Action Groups qui notifient l'équipe concernée.

À retenir

Distinguez bien métriques, logs et alertes : les métriques montrent l'état, les logs expliquent le détail, les alertes préviennent ou déclenchent une action.

Corrigé — réponses aux quiz

Les réponses attendues pour chaque quiz de révision du document, module par module, y compris les trois quiz de synthèse du Module 10.

Corrigé — Module 1 : Concepts cloud

1. Votre application doit absorber un pic de charge pendant deux heures. Quel bénéfice cloud est concerné ?

Réponse — L'élasticité — la capacité s'ajuste automatiquement à la hausse pendant le pic, puis revient à la normale ensuite.

2. Dans un modèle IaaS, qui a la responsabilité de mettre à jour le système d'exploitation invité ?

Réponse — Le client. En IaaS, Azure gère l'infrastructure physique, mais le client gère l'OS, le runtime, les applications et les données.

3. Quel modèle de déploiement cloud combine des ressources locales et du cloud public ?

Réponse — Le cloud hybride.

4. Pourquoi l'OpEx est-il souvent plus flexible que le CapEx ?

Réponse — Parce qu'il n'y a pas d'investissement initial lourd à amortir : la dépense suit la consommation réelle et peut être ajustée rapidement à la hausse comme à la baisse.

Corrigé — Module 2 : Architecture Azure

1. Quelle est la différence entre une région et une zone de disponibilité ?

Réponse — Une région est un emplacement géographique regroupant un ou plusieurs datacenters. Une zone de disponibilité est une séparation physique (un datacenter ou groupe de datacenters indépendant) à l'intérieur d'une même région.

2. À quoi sert une subscription ?

Réponse — C'est l'unité de facturation, de limites techniques et de gestion des accès dans Azure.

3. Pourquoi créer plusieurs resource groups plutôt qu'un seul ?

Réponse — Pour regrouper les ressources qui partagent un même cycle de vie (par environnement, équipe, application ou budget) et faciliter leur gestion, leur suppression groupée et l'application de droits RBAC ciblés.

4. Quel niveau de la hiérarchie permet d'appliquer une policy à plusieurs subscriptions à la fois ?

Réponse — Le management group.

Corrigé — Module 4 : Réseau

1. Quel service filtre des ports réseau au niveau d'une VM ?

Réponse — Le Network Security Group (NSG).

2. Quel service choisir pour une connexion privée dédiée vers Azure ?

Réponse — ExpressRoute.

3. Pourquoi Application Gateway est-il plus adapté au HTTP qu'un Load Balancer ?

Réponse — Parce qu'il opère en couche 7 (HTTP/HTTPS) et peut router le trafic selon l'URL ou le nom d'hôte, alors que le Load Balancer opère en couche 4 (TCP/UDP) sans comprendre le contenu applicatif.

4. À quoi sert le peering entre deux VNets ?

Réponse — À permettre la communication directe entre deux réseaux virtuels, sans passer par Internet.

Corrigé — Module 5 : Stockage et données

1. Quelle est la différence entre Blob Storage et Azure Files ?

Réponse — Blob Storage stocke des objets non structurés (images, logs, sauvegardes, documents). Azure Files est un partage de fichiers managé accessible via SMB/NFS, utilisable comme un lecteur réseau classique.

2. Quel service utiliser pour une base de données NoSQL mondiale ?

Réponse — Azure Cosmos DB.

3. Que signifie ZRS dans le contexte du stockage ?

Réponse — Zone-Redundant Storage : réplication synchrone des données entre plusieurs zones d'une même région.

4. Quel outil graphique permet d'explorer un storage account ?

Réponse — Storage Explorer.

Corrigé — Module 6 : Sécurité

1. Quelle est la différence entre Entra ID et RBAC ?

Réponse — Entra ID authentifie — il répond à « qui se connecte ? ». RBAC autorise — il répond à « que peut faire cette identité ? ».

2. Pourquoi utiliser le MFA ?

Réponse — Pour ajouter un facteur d'authentification supplémentaire et réduire le risque de compromission d'un compte, même si le mot de passe est compromis.

3. Quel service stocke les secrets applicatifs ?

Réponse — Key Vault.

4. Quel principe consiste à donner uniquement les droits strictement nécessaires ?

Réponse — Le principe du moindre privilège (least privilege).

Corrigé — Module 9 : Monitoring et gestion

1. Quel outil en ligne de commande est multiplateforme ?

Réponse — Azure CLI.

2. Quel service surveille métriques, logs et alertes ?

Réponse — Azure Monitor.

3. Quel outil donne des recommandations personnalisées ?

Réponse — Azure Advisor.

4. Quel outil aide à diagnostiquer une application web lente ?

Réponse — Application Insights.

Corrigé — Module 10 : révision examen (trois quiz de synthèse)

Quiz final — Concepts cloud

1. Donnez un exemple de PaaS et expliquez pourquoi ce n'est pas de l'IaaS.

Réponse — Azure App Service : Azure gère l'OS et le runtime, le client déploie seulement son code et gère ses données. En IaaS, le client gérerait en plus l'OS et le runtime lui-même (cas d'une Virtual Machine).

2. Quelle notion permet d'augmenter rapidement la capacité pendant un pic de charge ?

Réponse — L'élasticité (associée à la scalabilité).

3. Dans un modèle SaaS, que gère principalement le client ?

Réponse — La configuration de l'application et la gestion de ses comptes/utilisateurs — Microsoft gère toute la couche technique sous-jacente.

4. Pourquoi le cloud ne supprime-t-il pas toute responsabilité de sécurité ?

Réponse — À cause du modèle de responsabilité partagée : les données, les identités, les accès et certains choix de configuration restent toujours de la responsabilité du client, quel que soit le modèle de service (IaaS, PaaS ou SaaS).

Quiz final — Services Azure

1. Quel service stocke des objets non structurés ?

Réponse — Blob Storage.

2. Quel service est adapté à une API web sans gestion de serveur ?

Réponse — App Service (PaaS) — on y déploie du code sans gérer de serveur. Azure Functions convient aussi pour une exécution événementielle plus courte.

3. Quel service relie Azure à un site local via connexion privée ?

Réponse — ExpressRoute.

4. Quel service NoSQL mondial est proposé par Azure ?

Réponse — Azure Cosmos DB.

Quiz final — Gouvernance et coûts

1. Quel outil impose que les ressources soient déployées seulement en Europe ?

Réponse — Azure Policy.

2. Quel outil envoie une alerte quand le budget est dépassé ?

Réponse — Cost Management (budgets et alertes de dépassement).

3. Quel service donne des recommandations de coût et de sécurité ?

Réponse — Azure Advisor.

4. Quel mécanisme empêche la suppression accidentelle d'une ressource ?

Réponse — Un resource lock (verrou de ressource), en particulier le mode CanNotDelete.
